## 4. 业务流程与依赖

主流程：创建工程 → 导入并校验基础数据 → 生成并发布场景与分类保供目标 → 现状承灾/平衡分析 → 提升策略对比 → 源储协同配置 → 配置后平衡与稳定复核 → 必要时黑启动恢复优化 → 方案归档与报告。

这不是强制逐页点击的向导：承灾与平衡均可使用已发布场景独立启动；承灾内部可以调用平衡计算。离网判别和黑启动也应能分析现状方案，不强制先做新增配置。黑启动针对失电恢复工况，不能把“离网判别通过”作为唯一启动条件。配置后必须建立新方案版本，不能覆盖现状设备。

数据管理维护事实底账；场景模块维护灾害、故障、出力修正及目标；分析模块保存计算快照与结果。数据管理中的“场景数据”改为只读引用/跳转，避免两个地方编辑同一场景。每次任务绑定工程ID、基础数据版本、场景版本、方案版本、算法版本、随机种子与参数快照。输入变化后已有结果标记“已过期”，保留历史查看能力。

## 6. 数据和指标口径

- 工程、节点、线路、负荷、场景、方案、任务分别使用唯一ID；禁止参考稿中线路与负荷共用L前缀造成歧义，建议LINE/LOAD等独立类型标识。
- 电源功率MW，储能功率MW与能量MWh分开；线路热限额按模型使用A/MVA/MW并显式定义功率因数与转换，电阻电抗注明Ω或标幺基准。
- 储能按设备维护SOC、充放电效率和上下限，不直接平均不同容量设备SOC。车辆增加出发位置、可达节点、行程/到位/接入时间、数量、燃料或能量约束。
- 负荷业务分类（基本保障/居民生活/一般）与可靠性等级、恢复优先级为独立字段，不能直接视为同一枚举。
- 运行阶段以小时/分钟描述灾害、离网、应急投入、恢复；规划阶段以年份描述建设投产。两套阶段分别建模，并显式关联。
- 电力平衡建议约定放电为正、充电为负：电源+外部输入+储能净出力=实际供电负荷+网损。计划削减与非计划缺供分别记录，禁止重复计入缺供损失。
- 缺供电量由时间步缺供功率积分；期望缺供电量由场景/样本权重加权。场景权重需归一化并注明条件概率口径。
- 负荷满足率须区分瞬时功率满足率、时段电量满足率和随机样本达标概率。目标保供时长、最大中断时间、首次违反目标时间分别定义。
- 灾害强度优先使用物理量（例如风速、覆冰厚度）；使用pu时必须显示基准及脆弱性映射。承灾裕度公式及边界判定条件需固化。
- 总成本明确投资、年运行费用、折现期、残值与缺供损失的换算；不允许把万元与万元/年直接相加。多目标权重需要归一化及量纲处理。
- 判定状态统一为满足/不满足/未校核；“临界”作为裕度标签另列。任何硬约束不满足不得显示总体满足，“基本满足”须有正式规则才可启用。

## 8. 页面状态及交互要求

每个计算模块统一“输入设置 / 任务状态 / 结果分析”结构；局部标签替代PPT分页。顶部持续显示当前工程、场景、方案及版本。全局导入/导出标明工程包，页面按钮标明导入数据或导出结果，避免作用范围不清。

任务状态：未配置、待校验、可运行、排队、运行、成功、失败、取消；结果另有过期状态。不可行与超时有可行解分别展示，不能均记作成功最优。查看结果不触发重算。切换工程时提示未保存修改；输入缺失定位字段；断开网络不影响本地任务。

数据导入先预览再提交；错误包含文件、工作表、行列、原因与修复建议。校验重复ID、节点引用、时间连续性、曲线覆盖、SOC范围、阶段冲突、预算与容量上下限。表格和图表共享筛选条件；所有导出保留单位、版本及计算条件。

## 9. 验收与实施顺序

第一阶段：工程管理、数据模型、离线导入校验、场景、统一导航、任务与版本机制。第二阶段：平衡、承灾、策略与配置算法接入及闭环。第三阶段：稳定判别、一二次黑启动、综合报告与示范算例验证。原型可用明确标识的演示数据，但正式计算接口不得返回伪造结果。

最低验收用例：
1. 断网新建工程到导出方案全流程成功，重启可恢复已保存版本。
2. 错误节点引用、缺时序、非法SOC被阻止提交并定位；正确文件可导入。
3. 同一数据、参数、算法版本与随机种子可复现实验结果。
4. 时序功率平衡及SOC能量守恒满足约定容差；缺供电量与表格积分一致。
5. 修改场景后旧结果标记过期；新方案不改变基准方案。
6. 无资源、预算不足、孤岛不连通、通信不可达时输出明确原因，不展示成功方案。
7. 配置前后使用同一场景集、时间范围及指标口径比较；报告数值与页面一致。
8. 黑启动每一步设备及通信可用性、负荷恢复和稳定校核可追溯。
9. 按R03—R08准备成果覆盖清单与基准测试记录；性能指标在约定测试环境下测量，不能用界面演示耗时代替。
